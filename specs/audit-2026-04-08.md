# IDMR AI — Pre-Auth Audit

**Date:** 2026-04-08
**Scope:** Full repo audit ahead of (1) users/auth, (2) per-user chat history, (3) SoundCloud links for the ~10 transcripts that have them. Also captures general usability/feature suggestions.

Good foundation overall — clean separation of retrieval/embeddings/UI, solid chunking heuristics, and the planner → retrieval → generator flow is a reasonable pattern. Below is what to tighten before bolting on the upcoming work.

## 1. Critical / correctness

### 1a. `match_chunks_filtered` exists in code but not in `supabase-setup.sql`
`src/lib/retrieval.ts:67` calls an RPC that isn't defined in the committed schema. Either it only lives in the Supabase dashboard (schema drift — new environments will break) or the "search within document" path silently errors. Add it to the committed schema:

```sql
create or replace function match_chunks_filtered(
  query_embedding vector(1536),
  filter_title text,
  match_count int default 10,
  match_threshold float default 0.1
) returns table (...) language sql stable as $$
  select ...
  from chunks
  where chunks.title ilike '%' || filter_title || '%'
    and 1 - (chunks.embedding <=> query_embedding) > match_threshold
  order by chunks.embedding <=> query_embedding
  limit match_count;
$$;
```

### 1b. Upsert conflict key is broken for transcripts
`scripts/embed.ts:97` uses `onConflict: "source,title,chunk_index,page"`, but transcripts have `page: null`. Postgres treats nulls as distinct in unique constraints by default, so re-running `embed` on transcripts inserts duplicates instead of upserting. Fix with `NULLS NOT DISTINCT` (Postgres 15+) or split into two constraints by source:

```sql
alter table chunks drop constraint chunks_unique_key;
alter table chunks add constraint chunks_unique_key
  unique nulls not distinct (source, title, chunk_index, page);
```

### 1c. Secret key is the app's only Supabase client
`src/lib/supabase.ts` uses the Secret key (legacy `SUPABASE_SERVICE_ROLE_KEY`). Note Supabase's new key naming:

| Old | New | Bypasses RLS? | Where to use |
|---|---|---|---|
| `anon` | **Publishable key** | No — respects RLS | Browser + server-with-user-session |
| `service_role` | **Secret key** | **Yes — bypasses RLS** | Server only, admin tasks |

The Secret key is **not** the anon equivalent — it ignores every RLS policy. That's fine for retrieval/embeddings (admin work), but the moment we add "list my conversations" or "save this message as user X", we **must** use the Publishable key + the user's session — otherwise RLS does nothing and any user can read any other user's chats.

Pre-bifurcate now:

```
src/lib/supabase/admin.ts   → Secret key, server only, for embeddings/retrieval/cron
src/lib/supabase/server.ts  → Publishable key + cookies, for user-scoped reads/writes
src/lib/supabase/client.ts  → Publishable key, browser
```

Use the new env var names (`SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`) to match the current Supabase dashboard.

### 1d. No `maxDuration` on the chat route
`src/app/api/chat/route.ts` streams LLM output but doesn't export `const maxDuration = 60` or set `runtime`. On Vercel the default timeout can cut long streams. Add both explicitly.

### 1e. No error handling in the chat route
No try/catch around `generateText`/`streamText`/retrieval. Any Anthropic/OpenAI/Supabase hiccup returns an unhelpful 500. Wrap with proper error responses and surface a user-facing message through the stream.

## 2. Architecture / AI SDK best practices

### 2a. Two sequential LLM calls is overkill
The planner → retrieval → generator pattern costs ~300-800ms of Haiku latency every turn and duplicates context. Modern AI SDK idiom is a single `streamText` with `stopWhen: stepCountIs(3)` and the retrieval tools defined with `execute` handlers — Sonnet decides whether to call them itself and streams tokens plus tool steps to the user in one round trip:

```ts
const result = streamText({
  model: anthropic("claude-sonnet-4-6"),  // ← also upgrade from sonnet-4-20250514
  system: systemPrompt,
  messages: convertToModelMessages(messages),
  tools: {
    search_by_content: tool({
      inputSchema: z.object({ query: z.string() }),
      execute: async ({ query }) => searchByContent(query),
    }),
    // ...
  },
  stopWhen: stepCountIs(3),
});
return result.toUIMessageStreamResponse();
```

Benefits: one model, lower latency, tool calls stream to the client as `tool-*` parts (so we can render "Searching transcripts for X…" live instead of a generic spinner), and the hand-rolled `for (const call of plannerResult.toolCalls)` loop goes away.

The Haiku planner was originally added as a cost optimization, but with Sonnet 4.6's tool-use reliability and the duplicated context being eliminated, the single-call architecture is both cheaper and faster in most cases. **Drop the planner entirely.** Haiku stays imported for fire-and-forget background work like conversation auto-titling (3d), where Sonnet would be wasteful.

### 2b. `messages` is implicitly `any`
`src/app/api/chat/route.ts:43` destructures without a type. Use `UIMessage[]` from `ai` and the manual `parts` parsing cleans up.

### 2c. Manual markdown renderer
`FormattedText` in `page.tsx` re-implements a subset of markdown and will break on anything fancier than bold/links/lists (code blocks, tables, nested lists, blockquotes). Use [`streamdown`](https://github.com/vercel/streamdown) (Vercel's streaming-aware markdown component built for AI SDK) or `react-markdown` + `remark-gfm`.

### 2d. Retrieval results aren't deduped
If the planner calls both `search_by_content` and `search_within_document`, the same chunks can appear twice and burn context budget. Dedupe by `(source, title, chunk_index)` and optionally re-rank the merged set (MMR or a simple cosine + title-match bonus).

### 2e. `ivfflat` with `lists=100` is suboptimal
On a few thousand chunks, switch to HNSW — better recall, no `lists` tuning:

```sql
create index on chunks using hnsw (embedding vector_cosine_ops);
```

### 2f. Query embedding caching
A tiny LRU keyed on query string saves OpenAI calls on repeat questions. Low priority.

### 2g. Consider `text-embedding-3-large`
With only ~thousands of chunks, the cost delta is trivial and recall improves measurably for theological/archaic vocabulary. Requires a re-embed pass and `vector(3072)`.

## 3. Prep for auth + per-user chat history

Doing this before auth makes the migration trivial.

### 3a. Normalize documents
Today `title`, `url`, `speaker`, `date` are repeated on every chunk row. Split:

```sql
create table documents (
  id bigserial primary key,
  source text not null,                 -- 'transcript' | 'textbook'
  title text not null,
  speaker text,
  date text,
  url text,                              -- idmr.net transcript URL
  soundcloud_url text,                   -- ← for upcoming feature
  unique (source, title)
);

alter table chunks add column document_id bigint references documents(id);
-- backfill, then drop title/speaker/date/url from chunks
```

This directly enables the SoundCloud feature (one row per transcript, not every chunk) and makes a future "browse by document" UI trivial.

### 3b. Chat history schema

```sql
create table conversations (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users(id) on delete cascade,
  title text,                          -- auto-generated from first user message
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);

create table messages (
  id uuid primary key default gen_random_uuid(),
  conversation_id uuid references conversations(id) on delete cascade,
  role text not null,                  -- 'user' | 'assistant'
  parts jsonb not null,                -- store UIMessage.parts directly
  created_at timestamptz default now()
);

-- RLS
alter table conversations enable row level security;
alter table messages enable row level security;
create policy "own convos" on conversations for all using (auth.uid() = user_id);
create policy "own messages" on messages for all using (
  exists (select 1 from conversations c
          where c.id = conversation_id and c.user_id = auth.uid())
);
```

Store the full `parts` array (not just text) so tool-call UI, citations, and any future attachments round-trip correctly.

### 3c. Persist on the server, not the client
`useChat({ id: conversationId })` + `streamText({ ..., onFinish: async ({ response }) => { await saveMessages(...) } })` is the canonical pattern. Drop localStorage persistence once auth lands — or keep it as an anonymous-user fallback with a "sign in to save this conversation" migration that POSTs the existing messages into a new conversation on first login.

### 3d. Auto-title conversations
On the first turn, kick off a cheap Haiku call in parallel with the main stream to generate a 3-5 word title; write it back to `conversations.title`. Users expect this from the ChatGPT UX.

### 3e. Auth choice: Supabase Auth
Already on Supabase. `@supabase/ssr` handles Next 16 App Router cookies cleanly. Email magic link + Google is usually enough.

## 4. SoundCloud link feature

With the `documents` table above:

1. Add `soundcloud_url` column (done, above).
2. One-time data script: a JSON map of `title → soundcloud_url` for the ~10 transcripts, run an update.
3. In `retrieval.ts`, join `documents` so `ChunkResult` carries `soundcloud_url`.
4. In `route.ts`'s context formatter, include it alongside the idmr.net URL when present.
5. Update the system prompt: *"For transcripts with a SoundCloud link, include it as a second markdown link labeled 'Listen on SoundCloud' after the transcript link."*

**Alternative:** skip the LLM and render citations as structured UI from a `sources` tool-call part. Cleaner because the model can't hallucinate a URL, but more client work. Do option A first.

## 5. Feature ideas worth considering

Ranked roughly by value/effort:

- **Streaming tool-call visibility** — render "Searching transcripts for *'carnal mind'*…" while Sonnet works, using AI SDK's tool-step parts. Huge UX improvement, ~free once we collapse to single-call architecture.
- **Citation hover cards** — on hover over `[Source 1]`, show the chunk excerpt + speaker/date in a tooltip. Much better than the current "dump URLs at the bottom" approach.
- **Suggested follow-ups** — after each assistant response, generate 3 contextual follow-up questions with a cheap Haiku call. Big engagement lift.
- **Conversation sharing** — `/share/[id]` public read-only view. Natural virality for a niche knowledge base.
- **"Compare teachings" mode** — ask the model to compare how two transcripts / the textbook treat the same topic side-by-side. Plays directly to IDMR users who study cross-references.
- **Regenerate + copy** buttons on each assistant message. Standard chatbot table stakes.
- **Browse-by-document** page — list all 99 transcripts + textbook with filters (speaker, date, has-soundcloud). Useful even without AI.
- **Rate-limit the chat endpoint** before launching auth — `@upstash/ratelimit` keyed on IP (pre-auth) or user_id (post-auth). Cheap defense against runaway Anthropic spend.
- **Per-response feedback** (thumbs up/down + optional note) stored against the message — invaluable for evaluating retrieval quality once we have real traffic.
- **Quote-of-the-day** on the empty state — surfaces a random chunk, doubles as discoverability.
- **Keyword highlighting** in cited chunks when shown in hover cards.
- **Export conversation** as markdown/PDF — this audience skews toward serious study.
- **Semantic search over past conversations** once history lands.
